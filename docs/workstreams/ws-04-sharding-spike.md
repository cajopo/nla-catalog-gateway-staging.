# WS-04 — Shopify-native sharding spike

## Executive verdict

**Mechanically feasible, rejected as the primary storefront architecture.**

The frozen 28 August dataset can be partitioned into deterministic integer ranges over the verified PowerTools/source identifier. On the currently `ACTIVE` and Online Store-published baseline:

| Game | Products | Shards at 24,999 | Shards at 4,999 |
|---|---:|---:|---:|
| Magic | 122,534 | 5 | 25 |
| Pokémon | 71,604 | 3 | 15 |
| Yu-Gi-Oh! | 85,991 | 4 | 18 |
| One Piece | 11,662 | 1 | 3 |
| **Total** | **291,791** | **13** | **61** |

All active source IDs in this snapshot are numeric and unique within each game. The simulation assigns every product exactly once and keeps every shard under the requested cap.

The 24,999 scheme only avoids the storefront deep-pagination window. It does **not** preserve Shopify native filtering on these collections; staying below 5,000 requires 61 collections now, before the announced sealed expansion. Search, global sorting, facet counts, stable URLs, shard rebalancing and cross-shard navigation would still require a custom aggregation layer.

Therefore:

- `NO-GO` as the main solution;
- `GO-LIMITED` only as an optional SEO/fallback partition after the gateway is stable;
- no live smart collection should be created merely to prove integer ranges that are already reproducible offline.

## Reproducible command

```bash
python scripts/simulate_shopify_shards.py /path/to/catalog_gateway.sqlite3 \
  --caps 24999 4999 \
  --output /tmp/ws-04-sharding-simulation.json
```

The script opens SQLite in read-only mode, runs `PRAGMA quick_check`, rejects nonnumeric identifiers, never splits duplicate identifier buckets and emits a SHA-256 over the product IDs assigned to each shard.

## Current limitation discovered

The frozen database has no `record_type` column. It contains the four live `Magic Display` products but models their commercial box title as a searchable canonical name. Consequently this report can prove the range mechanics for the historical mixed projection, but it cannot provide honest `game × single/sealed/accessory` shard counts.

A class-aware rerun is required after WS-01 and WS-01B produce the new canonical snapshot. That rerun is not expected to reverse the architectural verdict; separating classes can only retain or increase the operational collection count.

## PowerTools compatibility

The simulation does not modify products, metafields or PowerTools. Integer range membership is derived from the identifier already used to link Shopify and PowerTools records. No evidence suggests that read-only collection membership alone would alter synchronization, but this report does not claim a live compatibility test. A live pilot would be a separate, reversible Shopify mutation and is unnecessary for the gateway decision already taken.

## Acceptance result

- deterministic range generation: PASS;
- 291,791 active published products accounted for exactly once: PASS;
- maximum 24,999 per deep-pagination shard: PASS;
- maximum 4,999 per native-filter shard: PASS;
- class-aware simulation: BLOCKED by missing `record_type` in the frozen schema;
- primary architecture: NO-GO;
- limited fallback/SEO use: CONDITIONAL GO after gateway staging.
